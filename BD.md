### 1. Які основні типи баз даних існують і в чому різниця між реляційними та нереляційними СУБД? Поясніть, які задачі краще вирішують SQL і NoSQL бази даних, які є основні категорії нереляційних БД та в яких сценаріях вони доцільні.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Бази даних діляться на два великих класи: **реляційні (SQL)** і **нереляційні (NoSQL)**. Реляційні зберігають дані в таблицях із чітко визначеною схемою, підтримують ACID-транзакції і потужний мову запитів SQL. NoSQL — широке поняття, що об'єднує різні підходи до зберігання даних: документи, ключ-значення, колонки, графи. Вони жертвують жорсткою схемою і частиною гарантій заради масштабованості та гнучкості.

---

#### Реляційні БД (SQL)

Дані зберігаються у таблицях із рядками і стовпцями. Таблиці пов'язані через зовнішні ключі. Схема жорстка — структура визначається наперед.

**Ключові властивості:**
- ACID-транзакції (Atomicity, Consistency, Isolation, Durability)
- Потужні JOIN-запити між таблицями
- Строга типізація і constraints (FK, UNIQUE, NOT NULL)
- Вертикальне масштабування (складніше горизонтальне)

**Приклади:** PostgreSQL, MySQL, MariaDB, Oracle, MSSQL

**Коли доцільні:** фінансові системи, ERP, e-commerce, будь-де де важлива цілісність даних і складні зв'язки між ними.

---

#### Нереляційні БД (NoSQL)

**Document stores** — зберігають документи (JSON/BSON). Гнучка схема, вкладені структури.
```
MongoDB, CouchDB
Коли: каталоги продуктів, CMS, профілі користувачів з різними полями
```

**Key-Value stores** — найпростіша модель: ключ → значення. Надзвичайно швидко.
```
Redis, Memcached, DynamoDB
Коли: кеш, сесії, лічильники, rate limiting, черги
```

**Wide-column stores** — рядки можуть мати різні набори колонок. Добре для великих обсягів з простими запитами.
```
Cassandra, HBase
Коли: IoT, логи, time-series, аналітика петабайтних даних
```

**Graph databases** — вузли і ребра. Оптимізовані для обходу зв'язків.
```
Neo4j, Amazon Neptune
Коли: соціальні мережі, рекомендації, fraud detection, knowledge graphs
```

**Time-series databases** — оптимізовані для послідовних часових даних.
```
InfluxDB, TimescaleDB
Коли: метрики, моніторинг, фінансові котирування
```

---

#### SQL vs NoSQL — порівняння

| | SQL | NoSQL |
|---|---|---|
| Схема | Жорстка, наперед визначена | Гнучка або без схеми |
| Транзакції | ACID повністю | Зазвичай BASE або обмежений ACID |
| Масштабування | Вертикальне (складніше горизонтальне) | Горизонтальне (sharding) |
| Запити | Потужний SQL, JOIN | Обмежені або специфічні для типу |
| Цілісність | Сувора (FK, constraints) | На відповідальності застосунку |
| Зрілість | Десятиліттями перевірені | Молодші, різноманітніші |

---

#### BASE vs ACID

NoSQL системи часто дотримуються **BASE**:
- **Basically Available** — система завжди відповідає, але відповідь може бути не найактуальнішою
- **Soft state** — стан може змінюватись без вхідних даних (реплікація)
- **Eventually consistent** — врешті-решт дані будуть узгоджені

---

#### Polyglot persistence

На практиці сучасні системи використовують кілька БД одночасно:

```
PostgreSQL  — основні бізнес-дані, транзакції
Redis       — кеш, сесії, черги
Elasticsearch — повнотекстовий пошук
MongoDB     — гнучкі документи (каталог, логи)
InfluxDB    — метрики і моніторинг
```

---

#### Міні-шпаргалка

- **SQL** — ACID, JOIN, жорстка схема → фінанси, ERP, складні зв'язки
- **Document** (MongoDB) → гнучкі структури, каталоги
- **Key-Value** (Redis) → кеш, сесії, лічильники
- **Wide-column** (Cassandra) → великі обсяги, time-series, IoT
- **Graph** (Neo4j) → зв'язки між об'єктами, рекомендації
- На практиці — polyglot: різні БД для різних задач

</details>

### 2. Які основні storage engine існують у MySQL і чим вони відрізняються? Поясніть різницю між InnoDB та MyISAM, їхні переваги, обмеження та типові сценарії використання.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Storage engine — це компонент MySQL, що відповідає за фізичне зберігання даних, індексування і виконання операцій. MySQL дозволяє вибирати engine для кожної таблиці окремо. Два основних — **InnoDB** (дефолт з MySQL 5.5+) і **MyISAM** (старий дефолт). Для більшості сучасних застосунків правильний вибір — InnoDB.

```sql
-- Переглянути engine таблиці
SHOW TABLE STATUS LIKE 'orders'\G

-- Переглянути доступні engines
SHOW ENGINES;

-- Задати engine при створенні
CREATE TABLE logs (id INT, message TEXT) ENGINE = MyISAM;

-- Змінити engine
ALTER TABLE logs ENGINE = InnoDB;
```

---

#### InnoDB — основний engine

**Ключові характеристики:**
- **ACID-транзакції** — `BEGIN`, `COMMIT`, `ROLLBACK`
- **Row-level locking** — блокує тільки рядки що змінюються, не всю таблицю
- **Foreign keys** — підтримка зовнішніх ключів і каскадних операцій
- **MVCC** (Multi-Version Concurrency Control) — читачі не блокують писачів
- **Crash recovery** — redo log дозволяє відновитись після збою
- **Clustered index** — дані фізично зберігаються разом з PRIMARY KEY

**Файли зберігання:**
```
ibdata1          — системний tablespace
tablename.ibd    — дані і індекси таблиці (file-per-table)
ib_logfile0/1    — redo log
```

---

#### MyISAM — застарілий engine

**Ключові характеристики:**
- **Немає транзакцій** — немає COMMIT/ROLLBACK
- **Table-level locking** — будь-який запис блокує всю таблицю
- **Немає foreign keys**
- **Немає crash recovery** — після збою потрібен REPAIR TABLE
- **Full-text search** — у старих версіях MySQL тільки MyISAM підтримував FULLTEXT (тепер InnoDB теж підтримує)
- Окремі файли: `.frm` (структура), `.MYD` (дані), `.MYI` (індекси)

**Єдина перевага:** швидший COUNT(*) без WHERE — зберігає кількість рядків окремо.

---

#### Порівняння

| | InnoDB | MyISAM |
|---|---|---|
| Транзакції | ✓ ACID | ✗ |
| Блокування | Row-level | Table-level |
| Foreign keys | ✓ | ✗ |
| Crash recovery | ✓ | ✗ (потрібен REPAIR) |
| MVCC | ✓ | ✗ |
| COUNT(*) | Повний скан | O(1) — зберігається окремо |
| Full-text search | ✓ (MySQL 5.6+) | ✓ |
| Пам'ять | Більше (buffer pool) | Менше |

---

#### Інші engines

**MEMORY (HEAP)** — зберігає дані в оперативній пам'яті. Дуже швидко, але дані зникають при рестарті. Корисно для тимчасових таблиць, lookup-таблиць.

```sql
CREATE TABLE temp_cache (id INT, data VARCHAR(255)) ENGINE = MEMORY;
```

**ARCHIVE** — стиснене зберігання, тільки INSERT і SELECT, без UPDATE/DELETE. Для логів і архівних даних що ніколи не змінюються.

**BLACKHOLE** — приймає дані але нічого не зберігає. Корисний для реплікації: master пише в BLACKHOLE, binlog передається на slave.

**CSV** — зберігає дані як CSV файли. Простий обмін даними, але без індексів.

**FEDERATED** — доступ до таблиць на віддаленому MySQL сервері.

---

#### Коли що використовувати

**InnoDB (майже завжди):**
- Будь-яке застосування де важлива цілісність даних
- Коли є одночасні читання і записи
- Коли потрібні транзакції або foreign keys
- Production системи будь-якої складності

**MyISAM (майже ніколи в новому коді):**
- Legacy системи де міграція надто дорога
- Read-only таблиці з дуже частим COUNT(*) без WHERE
- Full-text search на старих MySQL (до 5.6)

**MEMORY:**
- Тимчасові таблиці для складних обчислень
- Невеликі lookup-таблиці що інтенсивно читаються

---

#### InnoDB Buffer Pool

Ключовий параметр продуктивності InnoDB — `innodb_buffer_pool_size`. Це кеш сторінок даних і індексів в пам'яті. Чим більше — тим менше звернень до диску.

```sql
-- Рекомендовано: 70-80% доступної RAM на dedicated DB сервері
SET GLOBAL innodb_buffer_pool_size = 4 * 1024 * 1024 * 1024; -- 4GB

-- Поточний стан
SHOW STATUS LIKE 'Innodb_buffer_pool%';
```

---

#### Міні-шпаргалка

- **InnoDB** — дефолт, ACID, row-level lock, FK, crash recovery → для всього нового
- **MyISAM** — без транзакцій, table-lock, без FK → тільки legacy
- **MEMORY** — RAM-таблиці, швидко, зникають при рестарті → тимчасові дані
- **Вибір engine** — на рівні таблиці, можна мікс в одній БД
- **Buffer pool** — найважливіший параметр InnoDB, виставляти 70-80% RAM

</details>

### 3. Що таке шардінг, реплікація та партиціювання, і в чому різниця між цими підходами?

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Три різні техніки масштабування і організації даних у реляційних БД, які вирішують різні проблеми:
- **Реплікація** — копіювання даних на кілька серверів (доступність, читання)
- **Шардінг** — горизонтальне розбиття даних між серверами (горизонтальне масштабування запису)
- **Партиціювання** — розбиття таблиці на частини в межах одного сервера (продуктивність, управління даними)

---

#### Реплікація (Replication)

Дані копіюються з одного сервера (primary/master) на інші (replica/slave).

```
Primary (запис) → Replica 1 (читання)
                → Replica 2 (читання)
                → Replica 3 (резервна копія)
```

**Типи реплікації в MySQL:**

| Тип | Опис | Затримка |
|-----|------|----------|
| Async | Replica читає бінлог, primary не чекає | Можлива затримка |
| Semi-sync | Primary чекає підтвердження хоча б від 1 репліки | Мінімальна |
| Sync (Galera/Group Replication) | Всі ноди підтверджують транзакцію | Є latency |

**MySQL binlog-реплікація:**
```sql
-- На primary
SHOW MASTER STATUS;
-- File: mysql-bin.000001, Position: 154

-- На replica
CHANGE MASTER TO
  MASTER_HOST='primary-host',
  MASTER_LOG_FILE='mysql-bin.000001',
  MASTER_LOG_POS=154;
START SLAVE;
SHOW SLAVE STATUS\G
```

**Що дає:**
- Читання масштабується горизонтально (N реплік = N*throughput на read)
- High availability — failover при падінні primary
- Географічний розподіл читань

**Обмеження:**
- Запис все одно йде тільки в primary (вузьке місце)
- Реплікаційна затримка (replication lag) — репліки можуть відставати
- Split-brain при async failover

---

#### Шардінг (Sharding)

Горизонтальне розбиття даних між кількома серверами. Кожен сервер містить **підмножину рядків**.

```
User ID 1-1M    → Shard 1 (сервер A)
User ID 1M-2M   → Shard 2 (сервер B)
User ID 2M-3M   → Shard 3 (сервер C)
```

**Стратегії шардування:**

| Стратегія | Принцип | Плюс | Мінус |
|-----------|---------|------|-------|
| Range-based | По діапазону ключа | Простий range scan | Нерівномірне навантаження (hot shard) |
| Hash-based | `shard = hash(key) % N` | Рівномірний розподіл | Range queries складні |
| Directory-based | Lookup-таблиця | Гнучко | Додатковий запит до lookup |
| Geographic | По регіону/країні | Latency, compliance | Нерівномірний розподіл |

**Проблеми шардування:**

```
❌ JOIN між шардами — майже неможливий
❌ Розподілені транзакції — складно (2PC)
❌ Resharding — болісно при зміні кількості шардів
❌ Hotspot — якщо шард-ключ невдалий, один шард перегрівається
```

**Consistent Hashing** — вирішує проблему resharding:
- Ключі і сервери розміщуються на кільці
- При додаванні/видаленні сервера переміщується мінімум даних

**Де застосовується:**
- MongoDB — автошардування по shard key
- Cassandra — вбудований consistent hashing
- MySQL — ручне або через ProxySQL/Vitess

---

#### Партиціювання (Partitioning)

Таблиця логічно розбивається на **частини (партиції) в межах одного сервера**. Оптимайзер може звертатися тільки до потрібних партицій (partition pruning).

**Типи партиціювання в MySQL:**

```sql
-- RANGE — по діапазону значень
CREATE TABLE orders (
    id INT,
    created_at DATE,
    amount DECIMAL(10,2)
) PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p2022 VALUES LESS THAN (2023),
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);

-- LIST — по конкретних значеннях
CREATE TABLE users (
    id INT,
    country_code CHAR(2)
) PARTITION BY LIST COLUMNS(country_code) (
    PARTITION p_europe VALUES IN ('UA','DE','FR','PL'),
    PARTITION p_asia VALUES IN ('CN','JP','KR'),
    PARTITION p_other VALUES IN (DEFAULT)
);

-- HASH — рівномірний розподіл
CREATE TABLE sessions (
    id INT,
    user_id INT
) PARTITION BY HASH(user_id)
PARTITIONS 8;
```

**Partition Pruning:**
```sql
-- MySQL автоматично читає тільки потрібну партицію
EXPLAIN SELECT * FROM orders WHERE created_at BETWEEN '2023-01-01' AND '2023-12-31';
-- partitions: p2023  ← тільки одна партиція!
```

**Видалення старих даних:**
```sql
-- Замість DELETE мільйонів рядків:
ALTER TABLE orders DROP PARTITION p2022; -- миттєво!
```

---

#### Порівняльна таблиця

| | Реплікація | Шардінг | Партиціювання |
|--|-----------|---------|---------------|
| **Мета** | HA + read scale | Write scale | Query performance |
| **Де дані** | Повна копія на кожному | Підмножина на кожному | Частини на одному сервері |
| **JOIN** | Працює (в межах репліки) | Складно | Працює (прозоро) |
| **Транзакції** | Складно cross-node | Дуже складно | Повністю ACID |
| **Складність** | Середня | Висока | Низька |
| **Коли** | Читань більше ніж записів | Записів дуже багато | Велика таблиця, часте фільтрування |

---

#### Типова архітектура великого проекту

```
[App] → [ProxySQL/PgBouncer]
              ↓
    [Primary] ← запис
    [Replica 1] ← читання (партиціоновані таблиці)
    [Replica 2] ← читання (звіти)
    [Replica 3] ← бекап

При виході за межі одного сервера:
    [Vitess / CitusDB / Сustom Sharding Layer]
        → Shard 1: users 0-999999
        → Shard 2: users 1000000-1999999
```

---

#### Міні-шпаргалка

- **Реплікація** — копія даних на N серверах; масштабує читання, дає HA
- **Шардінг** — рядки розподілені між серверами; масштабує запис, але ускладнює JOIN
- **Партиціювання** — розбиття таблиці на частини на одному сервері; прискорює queries і DROP PARTITION
- **Вибір стратегії:** спочатку реплікація → потім партиціювання → шардінг — останній крок
- **Consistent hashing** — дозволяє resharding з мінімальним переміщенням даних
- **Partition pruning** — MySQL сам обирає потрібні партиції при фільтрації

</details>

### 4. Що таке нормалізація бази даних і навіщо вона потрібна? Що таке денормалізація, коли її доцільно використовувати і які компроміси вона створює?

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Нормалізація — процес організації таблиць для усунення надлишковості даних і аномалій при вставці, оновленні та видаленні. Денормалізація — свідоме порушення нормальних форм заради продуктивності читання. Це класичний trade-off: нормалізація оптимізує запис і зберігання, денормалізація — читання.

---

#### Аномалії без нормалізації

```sql
-- Одна таблиця orders з дублюванням даних клієнта
| order_id | customer_name | customer_email    | product  | price |
|----------|---------------|-------------------|----------|-------|
| 1        | John          | john@example.com  | Phone    | 500   |
| 2        | John          | john@example.com  | Laptop   | 1200  |

-- Аномалія оновлення: зміна email у John потребує UPDATE всіх рядків
-- Аномалія видалення: видалення єдиного замовлення видаляє і клієнта
-- Аномалія вставки: не можна додати клієнта без замовлення
```

---

#### Нормальні форми

**1NF (Перша нормальна форма)**
- Кожна клітинка містить атомарне значення (не список, не масив)
- Немає повторюваних груп колонок

```sql
-- Порушення 1NF
| id | name | phones          |
| 1  | John | 111, 222, 333   |  ← не атомарно

-- 1NF
| id | name | phone |
| 1  | John | 111   |
| 1  | John | 222   |
```

**2NF (Друга нормальна форма)**
- Відповідає 1NF
- Кожен неключовий атрибут повністю залежить від усього первинного ключа (немає часткових залежностей)

```sql
-- Порушення 2NF (складений ключ order_id + product_id)
| order_id | product_id | product_name | quantity |
-- product_name залежить тільки від product_id, не від усього ключа

-- 2NF: виносимо продукт в окрему таблицю
products: (product_id, product_name)
order_items: (order_id, product_id, quantity)
```

**3NF (Третя нормальна форма)**
- Відповідає 2NF
- Немає транзитивних залежностей (неключовий атрибут не залежить від іншого неключового)

```sql
-- Порушення 3NF
| employee_id | department_id | department_name |
-- department_name залежить від department_id, а не від employee_id

-- 3NF
departments: (department_id, department_name)
employees: (employee_id, department_id)
```

**BCNF (Боуса-Кодда)** — посилена 3NF, кожна функціональна залежність іде від суперключа.

На практиці 3NF достатньо для більшості застосунків.

---

#### Переваги нормалізації

- Дані зберігаються в одному місці → немає дублювання
- UPDATE/DELETE/INSERT без аномалій
- Менше місця на диску
- Легше підтримувати цілісність даних

---

#### Денормалізація

Свідоме порушення нормальних форм для прискорення читання. Додаємо надлишкові дані туди, де вони часто потрібні, щоб уникнути JOIN.

```sql
-- Нормалізовано: потрібен JOIN
SELECT o.id, c.name, c.email
FROM orders o
JOIN customers c ON o.customer_id = c.id;

-- Денормалізовано: дані вже в таблиці orders
SELECT id, customer_name, customer_email FROM orders;
-- Швидше, але customer_name дублюється в кожному рядку
```

**Типові прийоми:**

```sql
-- 1. Кешовані агрегати
ALTER TABLE products ADD COLUMN reviews_count INT DEFAULT 0;
ALTER TABLE products ADD COLUMN avg_rating DECIMAL(3,2) DEFAULT 0;
-- Оновлюємо при кожному новому review — не рахуємо COUNT(*) щоразу

-- 2. Дублювання часто читаних полів
ALTER TABLE orders ADD COLUMN customer_name VARCHAR(255);
-- Не потрібен JOIN для відображення списку замовлень

-- 3. Матеріалізовані представлення (PostgreSQL)
CREATE MATERIALIZED VIEW order_summary AS
SELECT o.id, c.name, SUM(oi.price) as total
FROM orders o JOIN customers c ... JOIN order_items oi ...
GROUP BY o.id, c.name;

REFRESH MATERIALIZED VIEW order_summary; -- оновлення за розкладом
```

---

#### Коли денормалізувати

- Read-heavy системи де JOIN дорогі (звіти, аналітика, дашборди)
- Data warehouse і OLAP — там денормалізація є нормою (star schema, snowflake)
- Коли профайлер показує що конкретний JOIN — вузьке місце
- Кешовані лічильники (likes_count, comments_count) — щоб не рахувати COUNT щоразу

---

#### Компроміси денормалізації

| | Нормалізація | Денормалізація |
|---|---|---|
| Запис | Швидший, без аномалій | Потрібно оновлювати всі копії |
| Читання | Потрібні JOIN | Швидше, дані вже є |
| Місце | Менше | Більше (дублювання) |
| Цілісність | Сувора | На відповідальності застосунку |
| Складність коду | Простіше | Складніше (підтримка консистентності) |

---

#### Міні-шпаргалка

- **1NF** — атомарні значення; **2NF** — немає часткових залежностей; **3NF** — немає транзитивних
- **Нормалізація** → без дублювання, без аномалій, легке оновлення
- **Денормалізація** → швидке читання, ціна — складність запису і ризик розсинхронізації
- **Кешовані агрегати** (likes_count) — найпоширеніша денормалізація
- **Матеріалізовані views** — денормалізація на рівні БД з автооновленням
- **Правило**: спочатку нормалізуй, потім денормалізуй там де є вимірений performance issue
