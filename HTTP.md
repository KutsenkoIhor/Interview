### 1. Що відбувається з моменту, коли користувач вводить URL у браузері, і до моменту отримання відповіді від сервера? Розкажіть про DNS resolution, hosts, TCP/TLS handshake, HTTP-запит, обробку на сервері та повернення відповіді в браузер.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Коли користувач вводить URL у браузері, починається цілий ланцюжок дій: браузер спочатку розбирає URL, визначає протокол, домен, порт, path, query params. Далі він намагається зрозуміти, на яку IP-адресу потрібно йти — для цього перевіряє кеш, файл hosts, а потім за потреби робить DNS resolution. Коли IP знайдено, браузер встановлює з сервером мережеве з'єднання: спочатку через TCP handshake, а якщо сайт працює по HTTPS — ще й через TLS handshake для шифрування та перевірки сертифіката.

Після цього браузер відправляє HTTP-запит: наприклад `GET /products?id=10 HTTP/1.1` або HTTP/2 frame. У запиті є method, path, headers, cookies, інколи body. Запит доходить до веб-сервера або reverse proxy, наприклад Nginx чи Apache. Далі сервер вирішує, що з ним робити: віддати статичний файл, прокинути в PHP-FPM, у Symfony/Laravel/Yii2, у мікросервіс, у балансувальник, у кеш, у БД тощо.

На бекенді застосунок проходить стандартний pipeline: роутинг, middleware, автентифікація, авторизація, валідація, бізнес-логіка, звернення до кешу, БД, черг або зовнішніх API. Потім формується HTTP-відповідь: статус-код, headers, body. Ця відповідь повертається назад у браузер, браузер її парсить, обробляє headers, cookies, кешування, редіректи, а якщо це HTML — починає будувати DOM, завантажувати CSS, JS, картинки і рендерити сторінку.

На співбесіді важливо показати, що це не просто "браузер відправив запит і отримав відповідь", а що тут є кілька рівнів: DNS, мережа, TLS, HTTP, серверна обробка, інфраструктура і фінальний рендер у браузері.

---

#### DNS resolution

DNS resolution — це процес перетворення доменного імені, наприклад `example.com`, у IP-адресу. Браузер спочатку може перевірити власний DNS-кеш, потім ОС-кеш, далі файл hosts, і лише потім піти на DNS resolver. Resolver може звертатися до кореневих DNS-серверів, TLD-серверів і авторитативного DNS-сервера домену. На практиці це часто кешується, тому повний ланцюг не завжди проходиться щоразу.

---

#### hosts

Файл hosts — це локальна ручна таблиця відповідностей домен → IP. Якщо в hosts є запис, він зазвичай має вищий пріоритет, ніж зовнішній DNS. Це часто використовують для локальної розробки, тестування або тимчасового перевизначення домену.

---

#### TCP handshake

Після отримання IP клієнт відкриває TCP-з'єднання. Класичний 3-way handshake: `SYN → SYN-ACK → ACK`. Після цього з'єднання вважається встановленим і по ньому можна передавати дані. TCP потрібен, бо HTTP потребує надійної доставки пакетів у правильному порядку.

---

#### TLS handshake

Якщо використовується HTTPS, після TCP виконується TLS handshake. Тут узгоджується версія TLS, набір шифрів, відбувається перевірка сертифіката сервера, обмін ключами і встановлення захищеного каналу. Це дає конфіденційність, цілісність даних і автентичність сервера. Якщо сертифікат невалідний, браузер покаже попередження.

---

#### HTTP-запит

Клієнт відправляє HTTP-запит, який складається з request line, headers і, за потреби, body. Наприклад: метод `GET`, шлях `/users/1`, headers типу `Host`, `Authorization`, `Cookie`, `Accept`. Для `POST`/`PUT`/`PATCH` зазвичай ще є body — JSON, form-data тощо.

---

#### Обробка на сервері

Спочатку запит приймає веб-сервер або reverse proxy. Далі він або сам віддає статичний контент, або передає далі в PHP-FPM / застосунок. У PHP-фреймворку далі зазвичай йдуть: front controller → router → middleware/kernel → controller/action → service layer → repository → DB/query builder/ORM → формується response object.

---

#### Повернення відповіді в браузер

Сервер повертає статус-код (200, 301, 404, 500), headers (`Content-Type`, `Cache-Control`, `Set-Cookie`), і body. Браузер читає це, може зберегти cookies, закешувати дані, перейти по редіректу, показати JSON або почати рендер HTML. Якщо HTML містить зовнішні CSS/JS/зображення, браузер робить додаткові HTTP-запити для них.

---

#### Міні-приклад

URL: `https://example.com/products/15?lang=uk`

```
1. Браузер розбирає URL:
   protocol: https, host: example.com, path: /products/15, query: lang=uk

2. Шукає IP:
   DNS cache → OS cache → hosts → DNS resolver

3. Встановлює з'єднання:
   TCP handshake → TLS handshake

4. Відправляє запит:
   GET /products/15?lang=uk HTTP/1.1
   Host: example.com
   Accept: text/html
   Cookie: PHPSESSID=abc123

5. Nginx приймає і передає в PHP-FPM.

6. Symfony/Yii2/Laravel:
   route → controller → middleware → service → DB → response

7. Сервер повертає:
   HTTP/1.1 200 OK
   Content-Type: text/html; charset=UTF-8
   Cache-Control: no-cache
   Set-Cookie: viewed_product=15; HttpOnly; Secure

8. Браузер отримує HTML, будує DOM і рендерить сторінку.
```

---

#### Міні-шпаргалка

- **URL** → parse → host, protocol, path, query
- **IP** шукається через cache → hosts → DNS
- **TCP handshake**, а для HTTPS ще **TLS handshake**
- Браузер шле **HTTP request**: method + headers + body
- Сервер обробляє через web server → app → DB → cache
- Відповідь: **status + headers + body**, браузер рендерить

</details>

### 2. Як працює DNS, які основні типи DNS-записів існують, і що відбудеться, якщо DNS-сервер недоступний? Поясніть роль записів A, AAAA, CNAME, MX, TXT, а також DNS cache на різних рівнях.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

DNS — це система, яка перетворює зрозумілі людині доменні імена, наприклад `example.com`, у технічні дані, найчастіше IP-адреси. Простими словами, DNS — це "телефонна книга" інтернету.

Процес працює так: клієнт спочатку перевіряє локальний кеш, потім може звернутися до локального resolver'а або DNS-сервера провайдера. Якщо там відповіді немає, починається рекурсивний пошук: від root DNS-серверів → TLD-серверів → авторитативного DNS-сервера конкретного домену. У результаті повертається потрібний запис із TTL.

На співбесіді важливо підкреслити, що DNS — це не тільки "знайти IP для сайту", а загальна система розподіленого зберігання записів про домен. І що кешування та TTL сильно впливають на поведінку системи, швидкість змін і відновлення після збоїв.

---

#### Як працює DNS (покроково)

Коли клієнт звертається до домену:

1. Браузерний кеш
2. Кеш ОС
3. Файл `hosts`
4. DNS resolver провайдера або корпоративний DNS
5. Якщо немає кешу — рекурсивний пошук: root DNS → TLD DNS → авторитативний DNS домену
6. Повертається запис + TTL

---

#### Типи DNS-записів

**A** — зв'язує домен з IPv4-адресою:
```
example.com -> 192.0.2.10
```

**AAAA** — те саме для IPv6:
```
example.com -> 2001:db8::10
```

**CNAME** — аліас одного доменного імені на інше (не на IP):
```
www.example.com -> example.com
```
> Потім DNS шукає реальний запис для `example.com`. CNAME не може співіснувати з іншими записами того ж імені.

**MX** — поштові сервери домену з пріоритетом:
```
example.com -> mail1.example.com  priority 10
example.com -> mail2.example.com  priority 20
```
Чим менше число — тим вищий пріоритет.

**TXT** — текстові дані. Використовується для:
- SPF — хто має право відправляти пошту від імені домену
- DKIM — криптографічне підтвердження пошти
- DMARC — політика перевірки пошти
- верифікації домену для Google, Cloudflare та інших сервісів

---

#### DNS cache на різних рівнях

Кеш може бути в кількох місцях:
- у браузері
- в операційній системі
- у локальному DNS resolver'і
- у DNS провайдера або корпоративного DNS
- у проміжних рекурсивних resolver'ах

Через це після зміни DNS-запису нове значення не завжди видно одразу — поки TTL не закінчився, різні клієнти можуть бачити стару відповідь.

---

#### Що буде, якщо DNS-сервер недоступний

Якщо є кеш із живим TTL — деякий час ще працює. Якщо кешу немає або TTL минув:
- сайт не відкриється по домену
- API по hostname стане недоступним
- поштові сервіси не зможуть знайти MX
- інші сервіси, що залежать від DNS, теж зламаються

"Навіть якщо сам application server працює, без DNS сервіс для користувача може виглядати як мертвий."

---

#### Міні-приклад

```
www.shop.com   CNAME   shop.com
shop.com       A       203.0.113.10
shop.com       AAAA    2001:db8::10
shop.com       MX      10 mail.shop.com
shop.com       TXT     "v=spf1 include:_spf.google.com ~all"
```

1. Браузер шукає `www.shop.com` → DNS повертає CNAME → `shop.com`
2. Шукається A або AAAA для `shop.com` → отримує IP
3. Браузер підключається до сервера
4. Поштовий сервер для `user@shop.com` дивиться MX
5. Email-система перевіряє SPF через TXT

Якщо DNS недоступний і кешу немає — зупинка вже на кроці 1–2.

---

#### Міні-шпаргалка

- **DNS** — перетворює домен у IP або інші службові дані
- **A** — IPv4, **AAAA** — IPv6
- **CNAME** — аліас на інший домен, не на IP
- **MX** — поштові сервери домену
- **TXT** — SPF, DKIM, DMARC, верифікації
- Якщо DNS недоступний — кеш ще може врятувати, без кешу домен не працює

</details>

### 3. У чому різниця між TCP, UDP та HTTP? Поясніть, які задачі вирішує кожен протокол і на якому рівні вони працюють.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

TCP, UDP і HTTP — це різні протоколи, які працюють на різних рівнях мережевої моделі і вирішують різні задачі. TCP і UDP — це транспортні протоколи: вони відповідають за доставку даних між хостами через мережу. HTTP — це протокол прикладного рівня: він визначає формат і семантику обміну даними між клієнтом і сервером і будується поверх TCP.

TCP забезпечує надійну доставку: з'єднання, порядок пакетів, підтвердження, повторна відправка при втраті. UDP — легший і швидший, але без гарантій доставки і порядку. HTTP — це вже "мова" запит-відповідь, яка використовує TCP як транспорт.

На співбесіді важливо показати розуміння рівнів: не просто "TCP надійний, UDP швидкий", а де кожен з них живе і чому вони не конкурують між собою, а доповнюють один одного.

---

#### Рівні мережевої моделі

```
Прикладний рівень     →  HTTP, HTTPS, FTP, SMTP, DNS
Транспортний рівень   →  TCP, UDP
Мережевий рівень      →  IP
Канальний рівень      →  Ethernet, Wi-Fi
```

TCP і UDP — транспортний рівень. HTTP — прикладний рівень поверх TCP.

---

#### TCP (Transmission Control Protocol)

TCP — надійний, з'єднання-орієнтований протокол. Перед передачею даних виконується 3-way handshake (`SYN → SYN-ACK → ACK`). Далі дані передаються з підтвердженням, перевіркою порядку і повторною відправкою при втраті.

Що гарантує TCP:
- доставка всіх пакетів
- правильний порядок
- цілісність даних
- контроль потоку і перевантаження

Де використовується: HTTP/HTTPS, email (SMTP, IMAP), SSH, FTP — скрізь, де важлива надійність.

Ціна: overhead на handshake, підтвердження, затримки при втраті пакетів.

---

#### UDP (User Datagram Protocol)

UDP — легкий, без з'єднання. Просто відправляє пакети (датаграми) без підтвердження і без гарантій. Якщо пакет загубився — UDP про це не знає і не повторює.

Що дає UDP:
- мінімальний overhead
- мала затримка
- можна відправляти broadcast/multicast

Де використовується:
- відеостримінг, VoIP, онлайн-ігри — де важлива швидкість, а втрата кількох пакетів некритична
- DNS — короткі запити, де швидкість важливіша за гарантію (і є retry на рівні клієнта)
- QUIC (HTTP/3) — будується поверх UDP, але додає свою логіку надійності

---

#### HTTP (HyperText Transfer Protocol)

HTTP — протокол прикладного рівня для обміну даними між клієнтом і сервером. Визначає формат запиту і відповіді: method, URL, headers, status code, body. Працює поверх TCP (HTTP/1.1, HTTP/2) або поверх UDP через QUIC (HTTP/3).

HTTP сам по собі не займається доставкою — цим займається TCP. HTTP визначає лише семантику: що запитати, як відповісти, які заголовки передати.

Версії:
- **HTTP/1.1** — одне з'єднання, один запит за раз (або keep-alive для повторного використання)
- **HTTP/2** — мультиплексування кількох запитів в одному TCP-з'єднанні, бінарний протокол, стиснення заголовків
- **HTTP/3** — поверх QUIC/UDP, вирішує проблему head-of-line blocking TCP

---

#### Порівняння

| | TCP | UDP | HTTP |
|---|---|---|---|
| Рівень | Транспортний | Транспортний | Прикладний |
| З'єднання | Є (handshake) | Немає | Поверх TCP/QUIC |
| Надійність | Гарантована | Не гарантована | Залежить від транспорту |
| Швидкість | Повільніший | Швидший | — |
| Де | HTTP, SSH, email | DNS, VoIP, стримінг, ігри | Web, API |

---

#### Чому HTTP/3 перейшов на UDP

HTTP/2 вирішив багато проблем HTTP/1.1, але залишилась одна: head-of-line blocking на рівні TCP. Якщо один TCP-пакет загубився, всі наступні чекають його повторної відправки, навіть якщо вони для різних потоків.

HTTP/3 використовує QUIC поверх UDP і реалізує власну логіку надійності та мультиплексування. Це дозволяє втрату одного пакету не блокувати інші потоки.

---

#### Міні-шпаргалка

- **TCP** — надійний транспорт з гарантіями, потрібний там де важлива цілісність
- **UDP** — швидкий транспорт без гарантій, потрібний там де важлива швидкість
- **HTTP** — прикладний протокол поверх TCP (або UDP через QUIC), визначає формат запит-відповідь
- TCP і UDP не конкурують з HTTP — вони на різних рівнях
- HTTP/3 побудований поверх UDP через QUIC, щоб вирішити проблеми TCP

</details>

### 4. Що таке мережеві порти і які стандартні порти найчастіше використовуються у веб-інфраструктурі? Наведіть приклади типових портів і поясніть їх призначення.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Мережевий порт — це числовий ідентифікатор від 0 до 65535, який разом з IP-адресою визначає конкретний сервіс або процес на хості. Якщо IP-адреса — це адреса будинку, то порт — це номер квартири. Один сервер може одночасно слухати на різних портах різні сервіси: наприклад, на 80 — HTTP, на 443 — HTTPS, на 3306 — MySQL.

Порти поділяються на три категорії: well-known (0–1023) — зарезервовані для стандартних протоколів, registered (1024–49151) — для відомих застосунків, dynamic/ephemeral (49152–65535) — тимчасові порти для клієнтських з'єднань.

На співбесіді важливо не просто перелічити порти, а показати розуміння навіщо вони взагалі потрібні і як це пов'язано з реальною інфраструктурою.

---

#### Як працює порт

Коли браузер відкриває `https://example.com`, він підключається до IP-адреси на порт 443. Якщо порт не вказаний явно в URL, браузер використовує дефолтний для протоколу: 80 для HTTP, 443 для HTTPS. Сервер слухає на цьому порту і обробляє вхідні з'єднання.

```
https://example.com        →  example.com:443
http://example.com         →  example.com:80
http://example.com:8080    →  example.com:8080
```

---

#### Стандартні порти у веб-інфраструктурі

| Порт | Протокол | Призначення |
|------|----------|-------------|
| 20, 21 | FTP | Передача файлів |
| 22 | SSH | Безпечне підключення до сервера |
| 25 | SMTP | Відправка пошти між серверами |
| 53 | DNS | Резолв доменів (UDP і TCP) |
| 80 | HTTP | Веб-трафік без шифрування |
| 110 | POP3 | Отримання пошти |
| 143 | IMAP | Отримання пошти з синхронізацією |
| 443 | HTTPS | Веб-трафік із шифруванням TLS |
| 465 / 587 | SMTP (TLS) | Відправка пошти з шифруванням |
| 993 | IMAPS | IMAP поверх TLS |
| 3306 | MySQL | База даних MySQL |
| 5432 | PostgreSQL | База даних PostgreSQL |
| 6379 | Redis | Кеш і черги Redis |
| 27017 | MongoDB | База даних MongoDB |
| 9200 | Elasticsearch | HTTP API Elasticsearch |
| 5672 | RabbitMQ | AMQP черги повідомлень |
| 8080, 8443 | HTTP/HTTPS | Альтернативні порти для dev/proxy |

---

#### Найважливіші для веб-розробника

**22 — SSH**: підключення до сервера для деплою, налагодження, адміністрування.

**80 — HTTP**: весь незашифрований веб-трафік. На практиці Nginx часто слухає на 80 і робить redirect на 443.

**443 — HTTPS**: весь сучасний веб-трафік з TLS. Саме сюди йдуть браузери за замовчуванням при HTTPS.

**3306 — MySQL / 5432 — PostgreSQL**: порти баз даних. У продакшені зазвичай закриті ззовні, доступні лише локально або з конкретних IP.

**6379 — Redis**: кеш, черги, сесії. Також зазвичай закритий ззовні.

**8080 / 8443**: часто використовуються для локальної розробки або для backend-сервісів за reverse proxy.

---

#### Порти і безпека

Відкритий порт — це потенційна точка входу. Тому базове правило: відкривати назовні тільки ті порти, які дійсно потрібні зовнішнім клієнтам. Наприклад:

- 80 і 443 — відкриті для всіх (веб)
- 22 — відкритий тільки для адміністраторів (або взагалі закритий і доступний через VPN)
- 3306, 6379, 5432 — закриті назовні, доступні тільки локально або між сервісами всередині мережі

На практиці це контролюється через firewall (iptables, ufw, security groups у хмарі).

---

#### Ephemeral ports

Коли браузер або клієнт відкриває з'єднання до сервера, ОС автоматично призначає клієнту тимчасовий порт із діапазону 49152–65535. Це так звані ephemeral ports. Вони існують тільки на час з'єднання і не потребують ручного призначення.

---

#### Міні-шпаргалка

- **Порт** — числовий ідентифікатор сервісу на хості (0–65535)
- **80** — HTTP, **443** — HTTPS, **22** — SSH, **53** — DNS
- **3306** — MySQL, **5432** — PostgreSQL, **6379** — Redis
- Якщо порт не вказаний в URL — браузер використовує дефолтний для протоколу
- У продакшені відкривати назовні тільки потрібні порти

</details>

<a id="5"></a>

### 5. У чому основні відмінності між HTTP/1.1 та HTTP/2? Поясніть, як вони впливають на продуктивність, роботу з'єднань і передачу даних.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

HTTP/1.1 і HTTP/2 — це версії одного протоколу прикладного рівня, але з принципово різним підходом до передачі даних. HTTP/1.1 з'явився у 1997 році і тривалий час був стандартом, але має ряд обмежень, які стають критичними на сучасних сторінках із десятками ресурсів. HTTP/2 був стандартизований у 2015 році і вирішує більшість із цих проблем без зміни семантики HTTP — методи, статус-коди, заголовки залишились ті самі.

Ключові відмінності: HTTP/2 підтримує мультиплексування кількох запитів в одному TCP-з'єднанні, використовує бінарний протокол замість текстового, стискає заголовки через HPACK і може ініціювати відправку ресурсів клієнту до того, як він їх запросив (server push).

---

#### HTTP/1.1 — основні обмеження

**One request per connection (без keep-alive)**

Спочатку кожен запит відкривав нове TCP-з'єднання. З HTTP/1.1 з'явився `keep-alive` — одне з'єднання можна перевикористовувати, але запити все одно йдуть послідовно.

**Head-of-line blocking**

Навіть із keep-alive наступний запит чекає відповіді на попередній. Якщо один запит повільний — всі наступні стоять у черзі.

**Текстовий протокол**

Заголовки передаються у вигляді plain text, що займає більше місця і повільніше парситься.

**Повторення заголовків**

У кожному запиті повторюються однакові заголовки: `Host`, `User-Agent`, `Cookie` тощо — навіть якщо вони не змінились.

**Workarounds у HTTP/1.1**

Через ці обмеження з'явились хаки: domain sharding (розподіл ресурсів по кількох доменах щоб паралельно відкривати більше з'єднань), CSS/JS bundling, image sprites — все це способи обійти обмеження протоколу, а не архітектурні рішення.

---

#### HTTP/2 — що змінилось

**Мультиплексування (multiplexing)**

Головна фіча. Кілька запитів і відповідей передаються паралельно в одному TCP-з'єднанні через окремі потоки (streams). Кожен потік незалежний — повільна відповідь одного не блокує інші.

```
HTTP/1.1:  [req1] → [resp1] → [req2] → [resp2]   (послідовно)
HTTP/2:    [req1, req2, req3] → [resp1, resp2, resp3]  (паралельно в одному з'єднанні)
```

**Бінарний протокол**

HTTP/2 передає дані не текстом, а бінарними фреймами. Це швидше парситься, менше займає місця і менш схильне до помилок.

**Стиснення заголовків (HPACK)**

Заголовки стискаються і кешуються між запитами. Однакові заголовки не повторюються повністю — передається лише diff. Це суттєво зменшує overhead, особливо при багатьох запитах із однаковими cookies і user-agent.

**Server Push**

Сервер може відправити ресурс клієнту ще до того, як клієнт його запросив. Наприклад, разом з HTML одразу відправити CSS і JS. На практиці ця фіча виявилась складною в реалізації і не завжди давала виграш — у HTTP/3 від неї фактично відмовились.

**Пріоритизація потоків**

Клієнт може вказати пріоритет для різних потоків — наприклад, CSS важливіший за зображення. Сервер може враховувати це при відправці.

---

#### Порівняння

| | HTTP/1.1 | HTTP/2 |
|---|---|---|
| З'єднання | Одне на запит або keep-alive (послідовно) | Одне для всіх запитів (паралельно) |
| Протокол | Текстовий | Бінарний |
| Заголовки | Повторюються в кожному запиті | Стискаються через HPACK |
| Head-of-line blocking | Є | Вирішено на рівні HTTP (але є на рівні TCP) |
| Server Push | Немає | Є (але рідко використовується) |
| Пріоритизація | Немає | Є |

---

#### Важливий нюанс: HTTP/2 і TLS

На практиці всі браузери підтримують HTTP/2 тільки поверх HTTPS. Технічно HTTP/2 можна використовувати і без TLS (h2c), але жоден браузер це не підтримує. Тому на практиці HTTP/2 = HTTPS.

---

#### Head-of-line blocking у HTTP/2

HTTP/2 вирішив head-of-line blocking на рівні HTTP, але не на рівні TCP. Якщо один TCP-пакет загубився — всі потоки в цьому з'єднанні чекають його повторної відправки. Саме цю проблему вирішує HTTP/3 через QUIC поверх UDP.

---

#### Чи потрібно щось міняти в коді для HTTP/2

Семантика HTTP не змінилась — ті самі методи, статус-коди, заголовки. Більшість застосунків не потребують змін у коді. HTTP/2 вмикається на рівні сервера (Nginx, Apache, CDN). Але деякі оптимізації для HTTP/1.1 (domain sharding, bundling усього в один файл) у HTTP/2 вже не потрібні або навіть шкідливі.

---

#### Міні-шпаргалка

- **HTTP/1.1** — текстовий, запити послідовно, заголовки повторюються, head-of-line blocking
- **HTTP/2** — бінарний, мультиплексування в одному з'єднанні, HPACK стискає заголовки
- **Основний виграш HTTP/2** — паралельна передача запитів без відкриття багатьох з'єднань
- **HTTP/2 на практиці** — тільки поверх HTTPS у браузерах
- **Залишилась проблема** — head-of-line blocking на рівні TCP, вирішується тільки в HTTP/3

</details>

<a id="6"></a>

### 6. Що таке SSL/TLS, як працює HTTPS і від чого саме він захищає? Поясніть TLS handshake, сертифікати, шифрування та обмеження HTTPS.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

SSL/TLS — це криптографічні протоколи, які забезпечують захищений канал поверх TCP. SSL (Secure Sockets Layer) — застаріла назва, TLS (Transport Layer Security) — його сучасна версія. Сьогодні коли кажуть "SSL", майже завжди мають на увазі TLS. HTTPS — це HTTP поверх TLS: браузер спочатку встановлює TLS-з'єднання, а вже всередині нього передає звичайний HTTP.

HTTPS захищає від трьох речей: перехоплення трафіку (конфіденційність), підміни даних у передачі (цілісність) і підміни сервера (автентичність). Але HTTPS не захищає від вразливостей у самому застосунку — XSS, SQL injection, CSRF залишаються актуальними незалежно від HTTPS.

---

#### TLS handshake — покроково

TLS handshake відбувається після TCP і до першого HTTP-запиту. Мета — узгодити параметри шифрування і встановити захищений канал.

```
1. Client Hello
   Клієнт відправляє: версії TLS які підтримує,
   список cipher suites, random bytes (client random)

2. Server Hello
   Сервер відповідає: обрана версія TLS,
   обраний cipher suite, random bytes (server random)

3. Certificate
   Сервер відправляє свій TLS-сертифікат

4. Перевірка сертифіката клієнтом
   Клієнт перевіряє: чи виданий CA якому довіряє,
   чи не прострочений, чи домен співпадає

5. Key exchange
   Обмін ключами (залежить від cipher suite)
   Наприклад через ECDHE генерується спільний секрет

6. Finished
   Обидві сторони підтверджують завершення handshake
   Далі весь трафік шифрується симетричним ключем
```

У TLS 1.3 handshake скорочений до одного round-trip (замість двох у TLS 1.2), що зменшує затримку.

---

#### Сертифікати

TLS-сертифікат — це цифровий документ, який підтверджує, що конкретний домен належить конкретній організації. Виданий Certificate Authority (CA) — довіреним центром сертифікації.

Сертифікат містить:
- доменне ім'я (або wildcard `*.example.com`)
- публічний ключ сервера
- хто видав (CA)
- термін дії
- цифровий підпис CA

Браузер перевіряє сертифікат по ланцюжку довіри: сертифікат сервера → intermediate CA → root CA. Root CA вбудовані в операційну систему та браузер.

Типи сертифікатів за рівнем перевірки:
- **DV (Domain Validated)** — перевіряється тільки контроль над доменом. Найшвидший і безкоштовний (Let's Encrypt).
- **OV (Organization Validated)** — додатково перевіряється організація.
- **EV (Extended Validation)** — найсуворіша перевірка, раніше показував зелений рядок в адресному барі.

---

#### Шифрування в TLS

TLS використовує два типи шифрування:

**Асиметричне** — під час handshake для обміну ключами. Публічний ключ відкритий, приватний — тільки на сервері. Повільне, тому використовується тільки для встановлення з'єднання.

**Симетричне** — для шифрування самих даних після handshake. Обидві сторони мають один спільний ключ сесії. Набагато швидше асиметричного.

Типовий cipher suite у TLS 1.3: `TLS_AES_256_GCM_SHA384` — AES-256 для шифрування даних, SHA-384 для перевірки цілісності.

---

#### Від чого захищає HTTPS

**Конфіденційність** — трафік між клієнтом і сервером зашифрований. Провайдер, хакер у мережі або man-in-the-middle бачать тільки зашифровані дані, але не їх зміст.

**Цілісність** — дані не можна непомітно змінити в дорозі. Будь-яка модифікація буде виявлена через MAC (Message Authentication Code).

**Автентичність** — клієнт впевнений, що спілкується з правильним сервером, а не підробкою. Це досягається через перевірку сертифіката.

---

#### Від чого HTTPS НЕ захищає

- **Вразливості застосунку** — XSS, SQL injection, CSRF, broken auth залишаються актуальними
- **Скомпрометований сервер** — якщо сервер зламано, HTTPS не допоможе
- **Скомпрометований клієнт** — якщо на машині шкідливе ПЗ або підроблений root CA
- **Metadata** — IP-адреса сервера, розмір трафіку та час запитів видно навіть при HTTPS
- **DNS** — сам DNS-запит (ім'я домену) традиційно не шифрується (але є DNS over HTTPS)

---

#### HSTS

HTTP Strict Transport Security — заголовок, який каже браузеру: ніколи не підключатись до цього домену по HTTP, тільки HTTPS. Захищає від downgrade-атак, коли зловмисник намагається змусити клієнта перейти на незашифроване з'єднання.

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

---

#### Міні-шпаргалка

- **TLS** — криптопротокол поверх TCP; HTTPS = HTTP + TLS
- **TLS handshake** — узгодження версії, cipher suite, обмін ключами, перевірка сертифіката
- **Сертифікат** — підтверджує автентичність домену, виданий CA
- **HTTPS захищає** — конфіденційність, цілісність, автентичність
- **HTTPS не захищає** — від вразливостей застосунку, від скомпрометованого сервера/клієнта
- **TLS 1.3** — швидший handshake (1 round-trip), безпечніші cipher suites

</details>

<a id="7"></a>

### 7. Чи можливо аналізувати або перехоплювати HTTPS-трафік, і за яких умов це можливо? Наприклад, через proxy, встановлений сертифікат або MITM у контрольованому середовищі.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Так, HTTPS-трафік можна аналізувати — але тільки за умови, що клієнт довіряє сертифікату перехоплювача. HTTPS шифрує трафік між двома кінцями, але якщо посередині стоїть proxy з власним сертифікатом, якому клієнт довіряє, то виходить два окремих TLS-з'єднання: клієнт ↔ proxy і proxy ↔ сервер. Proxy бачить весь трафік у відкритому вигляді.

Це і є класична MITM-схема (Man-in-the-Middle) — але в контрольованому середовищі вона абсолютно легітимна і широко використовується: корпоративні мережі, інструменти розробника, тестування API.

---

#### Як це працює технічно

```
Без proxy:
Браузер → [TLS] → Сервер
Браузер бачить сертифікат сервера, перевіряє, довіряє.

З MITM proxy:
Браузер → [TLS з сертифікатом proxy] → Proxy → [TLS з сертифікатом сервера] → Сервер
Proxy бачить увесь трафік у відкритому вигляді між двома з'єднаннями.
```

Браузер не покаже попередження, якщо сертифікат proxy виданий CA, якому браузер довіряє — тобто якщо root сертифікат proxy встановлений у системне або браузерне сховище довірених CA.

---

#### Де це використовується легітимно

**Інструменти розробника**

Charles Proxy, Mitmproxy, Fiddler, Burp Suite — встановлюють власний root сертифікат у систему. Після цього браузер довіряє їхнім сертифікатам, і весь HTTPS-трафік можна інспектувати. Стандартна практика при розробці і тестуванні API.

**Корпоративні мережі**

Корпоративний firewall або proxy перехоплює весь HTTPS-трафік для DLP (Data Loss Prevention), антивіруса або контент-фільтрації. На корпоративних ноутбуках root сертифікат компанії встановлений через Group Policy автоматично.

**Мобільне тестування**

При тестуванні мобільних додатків проксують трафік через Charles або Mitmproxy — встановлюють сертифікат на пристрій вручну або через MDM.

**Тестування безпеки**

Burp Suite використовується для тестування на проникнення — перехоплення, модифікація і повторна відправка запитів.

---

#### Захист від MITM

**Certificate Pinning**

Застосунок "пам'ятає" конкретний сертифікат або публічний ключ сервера і відмовляється від з'єднання, якщо сертифікат не збігається — навіть якщо він виданий довіреним CA. Використовується у мобільних додатках і критичних API.

Мінус: якщо сертифікат змінився (ротація) — треба оновлювати застосунок.

**HSTS Preloading**

Браузер заздалегідь знає, що домен працює тільки по HTTPS, і ніколи не ходить по HTTP — навіть при першому запиті.

**Certificate Transparency (CT)**

Публічний лог всіх виданих сертифікатів. Браузери можуть перевіряти, чи є сертифікат у цьому логу. Допомагає виявити несанкціоновано видані сертифікати.

---

#### Коли браузер покаже попередження

Браузер покаже помилку сертифіката якщо:
- сертифікат прострочений
- домен у сертифікаті не збігається з адресою
- сертифікат виданий CA, якому браузер не довіряє
- сертифікат відкликаний (перевірка через CRL або OCSP)
- порушений ланцюжок довіри

---

#### Важливий нюанс для співбесіди

"HTTPS не гарантує, що ніхто між клієнтом і сервером не бачить трафік — він гарантує, що трафік не можна прочитати без довіреного сертифіката. Якщо зловмисник або корпоративний proxy встановив свій root CA на клієнтській машині, HTTPS-трафік повністю відкритий для них."

---

#### Міні-шпаргалка

- **HTTPS можна перехопити** якщо клієнт довіряє сертифікату посередника
- **MITM proxy** (Charles, Mitmproxy, Burp) — легітимний інструмент розробки і тестування
- **Корпоративний proxy** — перехоплює HTTPS через встановлений root CA
- **Certificate Pinning** — захист від MITM на рівні застосунку
- **Браузер покаже попередження** тільки якщо сертифікат не пройшов перевірку

</details>

### 8. Для чого використовується OpenSSL на практиці? Наведіть типові приклади використання у розробці та DevOps.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

OpenSSL — це відкрита бібліотека і набір CLI-утиліт для роботи з криптографією, сертифікатами і TLS. На практиці вона використовується скрізь: генерація ключів і сертифікатів, перевірка TLS-з'єднань, інспекція сертифікатів, шифрування файлів, налагодження HTTPS. Для розробника і DevOps-інженера це базовий інструмент, без якого важко уявити роботу з будь-якою PKI-інфраструктурою.

---

#### Перевірка TLS-з'єднання і сертифіката

Найчастіше використовуваний сценарій — перевірити, який сертифікат повертає сервер, коли він закінчується і чи правильно налаштований TLS.

```bash
# Подивитись сертифікат сервера
openssl s_client -connect example.com:443

# Коротко — тільки дати і домен
openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates -subject

# Перевірити конкретний SNI (Server Name Indication)
openssl s_client -connect example.com:443 -servername example.com
```

Це корисно коли потрібно швидко перевірити: чи дійсний сертифікат, чи не прострочений, чи правильний CN/SAN.

---

#### Генерація приватного ключа і самопідписаного сертифіката

Для локальної розробки або внутрішніх сервісів часто потрібен self-signed сертифікат.

```bash
# Згенерувати приватний ключ RSA 2048
openssl genrsa -out private.key 2048

# Або сучасніший EC ключ
openssl ecparam -genkey -name prime256v1 -out private.key

# Створити самопідписаний сертифікат (діє 365 днів)
openssl req -new -x509 -key private.key -out cert.crt -days 365 \
  -subj "/CN=localhost/O=Dev/C=UA"

# Або ключ і сертифікат одночасно
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem \
  -days 365 -nodes -subj "/CN=localhost"
```

---

#### Генерація CSR (Certificate Signing Request)

Коли потрібен реальний сертифікат від CA — спочатку генерується CSR і відправляється в CA.

```bash
# Згенерувати ключ і CSR
openssl req -new -newkey rsa:2048 -nodes \
  -keyout domain.key -out domain.csr \
  -subj "/CN=example.com/O=MyCompany/C=UA"

# Перевірити вміст CSR
openssl req -text -noout -in domain.csr
```

---

#### Інспекція сертифіката

```bash
# Подивитись деталі сертифіката з файлу
openssl x509 -text -noout -in cert.crt

# Тільки дати
openssl x509 -noout -dates -in cert.crt

# Тільки subject і issuer
openssl x509 -noout -subject -issuer -in cert.crt

# Перевірити fingerprint
openssl x509 -noout -fingerprint -sha256 -in cert.crt
```

---

#### Конвертація форматів сертифікатів

Сертифікати бувають у різних форматах: PEM, DER, PKCS#12. OpenSSL конвертує між ними.

```bash
# PEM → DER
openssl x509 -in cert.pem -outform DER -out cert.der

# DER → PEM
openssl x509 -in cert.der -inform DER -out cert.pem

# Сертифікат + ключ → PKCS#12 (для Java, Windows, мобільних)
openssl pkcs12 -export -in cert.pem -inkey key.pem -out bundle.p12

# PKCS#12 → PEM
openssl pkcs12 -in bundle.p12 -out bundle.pem -nodes
```

---

#### Шифрування і дешифрування файлів

```bash
# Зашифрувати файл симетричним шифруванням (AES-256)
openssl enc -aes-256-cbc -salt -in secret.txt -out secret.enc -k mypassword

# Розшифрувати
openssl enc -d -aes-256-cbc -in secret.enc -out secret.txt -k mypassword
```

---

#### Перевірка ланцюжка сертифікатів

```bash
# Перевірити сертифікат відносно CA bundle
openssl verify -CAfile ca-bundle.crt cert.crt

# Перевірити з intermediate CA
openssl verify -CAfile root.crt -untrusted intermediate.crt cert.crt
```

---

#### Тестування підтримуваних версій TLS і cipher suites

```bash
# Перевірити які версії TLS підтримує сервер
openssl s_client -connect example.com:443 -tls1_2
openssl s_client -connect example.com:443 -tls1_3

# Перевірити конкретний cipher suite
openssl s_client -connect example.com:443 -cipher AES256-SHA
```

---

#### Генерація випадкових даних

```bash
# Згенерувати 32 байти випадкових даних у hex
openssl rand -hex 32

# У base64 (зручно для секретів, API ключів)
openssl rand -base64 32
```

Часто використовується для генерації APP_KEY, JWT secret, CSRF token seed та інших секретів у проектах.

---

#### Міні-шпаргалка

- **Перевірити сертифікат сервера** — `openssl s_client -connect host:443`
- **Подивитись деталі сертифіката** — `openssl x509 -text -noout -in cert.crt`
- **Згенерувати self-signed сертифікат** — `openssl req -x509 -newkey rsa:2048 ...`
- **Згенерувати CSR** — `openssl req -new -newkey rsa:2048 ...`
- **Конвертувати формати** — PEM ↔ DER ↔ PKCS#12
- **Згенерувати секрет** — `openssl rand -base64 32`

</details>

### 9. Як працює кеш браузера і які HTTP-заголовки керують кешуванням? Поясніть Cache-Control, ETag, Last-Modified, Expires, 304 Not Modified.

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

Кеш браузера — це механізм збереження відповідей від сервера локально, щоб не завантажувати один і той самий ресурс повторно. Браузер зберігає HTML, CSS, JS, зображення і при наступному запиті може або повністю взяти відповідь із кешу, або запитати сервер чи ресурс змінився. Управління цим процесом відбувається через HTTP-заголовки.

Є два сценарії кешування: **strong cache** — браузер взагалі не звертається до сервера, поки кеш живий; і **conditional request** — браузер запитує сервер, але той може відповісти `304 Not Modified` без тіла, що економить трафік.

---

#### Cache-Control

Головний заголовок для управління кешем. Може бути і в response (сервер → клієнт), і в request (клієнт → сервер/proxy).

**Основні директиви у response:**

```
Cache-Control: max-age=3600
```
Кеш живий 3600 секунд від моменту отримання. Браузер не звертається до сервера весь цей час.

```
Cache-Control: no-cache
```
Не означає "не кешувати". Означає: кешуй, але перед використанням завжди перевір у сервера чи актуально (conditional request).

```
Cache-Control: no-store
```
Взагалі не зберігати у кеші. Використовується для чутливих даних: банківські сторінки, особисті дані.

```
Cache-Control: public
```
Відповідь можна кешувати будь-ким — браузером, CDN, proxy.

```
Cache-Control: private
```
Кешувати тільки в браузері користувача, не в shared cache (CDN, proxy).

```
Cache-Control: must-revalidate
```
Якщо кеш прострочений — обов'язково перевірити у сервера, не використовувати застарілий кеш.

```
Cache-Control: s-maxage=86400
```
Те саме що `max-age`, але тільки для shared cache (CDN, proxy). Браузер ігнорує.

**Типові комбінації:**

```
# Статичні файли з hash у імені (app.abc123.js) — кешуємо назавжди
Cache-Control: public, max-age=31536000, immutable

# HTML-сторінки — завжди перевіряти
Cache-Control: no-cache

# Приватні дані — не кешувати взагалі
Cache-Control: no-store, private
```

---

#### Expires

Застарілий заголовок (HTTP/1.0), задає конкретну дату закінчення кешу:

```
Expires: Wed, 01 Jan 2026 00:00:00 GMT
```

Якщо є `Cache-Control: max-age` — він має пріоритет над `Expires`. На практиці `Expires` вже майже не використовують — `Cache-Control` гнучкіший і зрозуміліший.

---

#### ETag

ETag (Entity Tag) — це унікальний ідентифікатор версії ресурсу, який сервер генерує і повертає у response:

```
ETag: "abc123def456"
```

При наступному запиті браузер відправляє цей ETag назад:

```
If-None-Match: "abc123def456"
```

Сервер порівнює: якщо ресурс не змінився — повертає `304 Not Modified` без body. Якщо змінився — повертає `200` з новим ETag і тілом.

ETag може бути strong (`"abc123"`) або weak (`W/"abc123"`). Weak ETag означає, що ресурс "семантично еквівалентний", але не побайтово однаковий.

---

#### Last-Modified / If-Modified-Since

Альтернатива ETag на основі дати:

```
Last-Modified: Mon, 01 Jan 2024 12:00:00 GMT
```

Браузер при наступному запиті відправляє:

```
If-Modified-Since: Mon, 01 Jan 2024 12:00:00 GMT
```

Сервер відповідає `304` якщо не змінилось, або `200` з новим `Last-Modified`.

ETag надійніший за `Last-Modified`, бо дата змінюється при будь-якому торканні файлу, навіть якщо вміст не змінився. ETag — це хеш або версія контенту.

---

#### 304 Not Modified

Відповідь без body. Означає: "ресурс не змінився, використовуй те що в кеші."

```
HTTP/1.1 304 Not Modified
ETag: "abc123def456"
Cache-Control: max-age=3600
```

Браузер отримує 304 і відображає ресурс із локального кешу. Економить трафік і час завантаження.

---

#### Як це працює разом — повний flow

```
1. Перший запит:
   GET /app.js
   ← 200 OK
   ← Cache-Control: max-age=3600
   ← ETag: "v1"

2. Повторний запит протягом 3600 сек:
   Браузер взагалі не йде на сервер.
   Використовує кеш напряму (strong cache).

3. Після закінчення max-age:
   GET /app.js
   → If-None-Match: "v1"
   
   Якщо не змінилось:
   ← 304 Not Modified  (без body, кеш оновлюється)
   
   Якщо змінилось:
   ← 200 OK + новий контент
   ← ETag: "v2"
```

---

#### Stale-While-Revalidate

Сучасна директива: дозволяє використовувати застарілий кеш поки фоново оновлює його:

```
Cache-Control: max-age=60, stale-while-revalidate=300
```
Протягом 60 сек — свіжий кеш. Від 60 до 360 сек — повертає старий кеш і паралельно оновлює. Після 360 сек — блокує і чекає відповіді.

---

#### Vary

Вказує сервер, від яких request headers залежить відповідь:

```
Vary: Accept-Encoding
Vary: Accept-Language
```

Якщо один клієнт запросив gzip, а інший — без стиснення, це різні версії кешу. CDN і proxy враховують `Vary` при зберіганні.

---

#### Практичні патерни

**Статичні файли з fingerprint у імені** (`app.a1b2c3.js`):
```
Cache-Control: public, max-age=31536000, immutable
```
Ім'я файлу змінюється при кожному білді — кеш ніколи не застаріє, а нова версія завжди отримає новий URL.

**HTML-сторінки:**
```
Cache-Control: no-cache
ETag: "v42"
```
Завжди перевіряти, але 304 якщо не змінилось.

**API з динамічними даними:**
```
Cache-Control: no-store
```
Або короткий `max-age=60` для даних які рідко змінюються.

---

#### Міні-шпаргалка

- **Cache-Control: max-age** — strong cache, браузер не йде на сервер
- **Cache-Control: no-cache** — кешувати але завжди перевіряти (не "не кешувати"!)
- **Cache-Control: no-store** — взагалі не кешувати
- **ETag + If-None-Match** — перевірка за хешем вмісту
- **Last-Modified + If-Modified-Since** — перевірка за датою
- **304 Not Modified** — ресурс не змінився, використовуй кеш
- **Статичні файли з hash** — `max-age=31536000, immutable`
- **HTML** — `no-cache` + ETag

</details>

### 10. Що таке HTTP headers і cookies, як вони передаються між клієнтом і сервером, і як ними керувати?

<details>
<summary>Розкрити:</summary>

#### Загальна відповідь

HTTP headers — це службові метадані, які передаються разом із кожним запитом і відповіддю. Вони описують формат даних, авторизацію, кешування, cookies, CORS, security-політики та багато іншого. Cookies — це один зі способів передачі стану через headers: сервер встановлює їх через `Set-Cookie`, браузер автоматично повертає через `Cookie` у наступних запитах.

Важливо розуміти різницю між request headers (клієнт → сервер) і response headers (сервер → клієнт) — вони мають різне призначення і різний набір полів.

---

#### Структура HTTP-запиту і відповіді

**Request:**
```
GET /api/users HTTP/1.1
Host: example.com
Authorization: Bearer eyJhbGc...
Accept: application/json
Content-Type: application/json
Cookie: session_id=abc123; theme=dark
User-Agent: Mozilla/5.0 ...
```

**Response:**
```
HTTP/1.1 200 OK
Content-Type: application/json; charset=UTF-8
Cache-Control: no-cache
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax
X-Request-Id: f4a9b1c2
```

---

#### Основні request headers

| Header | Призначення |
|--------|-------------|
| `Host` | Домен і порт сервера. Обов'язковий у HTTP/1.1 |
| `Authorization` | Токен або credentials: `Bearer <token>`, `Basic <base64>` |
| `Content-Type` | Формат body запиту: `application/json`, `multipart/form-data` |
| `Accept` | Який формат відповіді очікує клієнт: `application/json` |
| `Cookie` | Cookies що браузер відправляє серверу |
| `User-Agent` | Інформація про клієнт (браузер, версія, ОС) |
| `Referer` | URL сторінки з якої прийшов запит |
| `Origin` | Origin клієнта, використовується у CORS |
| `X-Request-Id` | Унікальний ID запиту для трасування |
| `Accept-Encoding` | Підтримувані алгоритми стиснення: `gzip, br` |

---

#### Основні response headers

| Header | Призначення |
|--------|-------------|
| `Content-Type` | Формат body відповіді |
| `Set-Cookie` | Встановити cookie у браузері |
| `Cache-Control` | Правила кешування |
| `Location` | URL для редіректу (301, 302, 307) |
| `WWW-Authenticate` | Вказує тип auth при 401 |
| `Access-Control-Allow-Origin` | CORS: які origin дозволені |
| `Strict-Transport-Security` | HSTS: тільки HTTPS |
| `Content-Encoding` | Стиснення відповіді: `gzip`, `br` |
| `X-Frame-Options` | Захист від clickjacking |
| `Content-Security-Policy` | CSP: звідки дозволено завантажувати ресурси |

---

#### Cookies — як передаються

Сервер встановлює cookie через response header:
```
Set-Cookie: session_id=abc123; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

Браузер автоматично повертає у наступних запитах:
```
Cookie: session_id=abc123; theme=dark
```

Кілька cookies передаються в одному рядку через `;`.

---

#### Атрибути cookie

**`HttpOnly`** — cookie недоступна через `document.cookie` у JavaScript. Захист від XSS.

**`Secure`** — cookie передається тільки через HTTPS.

**`SameSite`** — контролює відправку cookie в cross-site запитах:
- `Strict` — тільки same-site запити
- `Lax` — same-site + top-level navigation (дефолт у сучасних браузерах)
- `None` — cross-site, але тоді обов'язково `Secure`

**`Max-Age`** / **`Expires`** — час життя. Без них — session cookie (до закриття браузера).

**`Path`** — для яких URL paths cookie відправляється.

**`Domain`** — для яких доменів і піддоменів. Наприклад `.example.com` включає всі субдомени.

#### Як керувати headers у PHP

**Request headers (що прийшли від клієнта):**
```php
// Через $_SERVER (більшість headers з префіксом HTTP_)
$auth = $_SERVER['HTTP_AUTHORIZATION'] ?? null;
$contentType = $_SERVER['CONTENT_TYPE'] ?? null;  // без HTTP_

// Через getallheaders()
$headers = getallheaders();
$token = $headers['Authorization'] ?? null;
```

**Response headers (що відправляємо клієнту):**
```php
header('Content-Type: application/json');
header('Cache-Control: no-store');
header('X-Request-Id: ' . uniqid());
```

**Cookies у PHP:**
```php
// Встановити
setcookie('session_id', 'abc123', [
    'expires'  => time() + 3600,
    'path'     => '/',
    'secure'   => true,
    'httponly' => true,
    'samesite' => 'Lax',
]);

// Прочитати
$sessionId = $_COOKIE['session_id'] ?? null;

// Видалити (встановити час у минулому)
setcookie('session_id', '', time() - 1, '/');
```

#### Як керувати headers у Symfony

```php
// Request headers
$token = $request->headers->get('Authorization');
$contentType = $request->headers->get('Content-Type');

// Response headers
$response->headers->set('X-Request-Id', Uuid::v4());
$response->headers->set('Cache-Control', 'no-store');

// Cookie у response
$cookie = Cookie::create('session_id')
    ->withValue('abc123')
    ->withExpires(new \DateTimeImmutable('+1 hour'))
    ->withSecure(true)
    ->withHttpOnly(true)
    ->withSameSite('lax');

$response->headers->setCookie($cookie);

// Прочитати cookie з request
$sessionId = $request->cookies->get('session_id');
```

#### Custom headers і конвенції

Custom headers зазвичай мають префікс `X-`:
```
X-Request-Id: f4a9b1c2
X-Api-Version: 2
X-RateLimit-Remaining: 42
```

Хоча `X-` більше не є офіційним стандартом, конвенція широко використовується. Стандартні кастомні headers реєструються через IANA.

#### Міні-шпаргалка

- **Headers** — службові метадані запиту/відповіді
- **Cookie** → сервер встановлює через `Set-Cookie`, браузер повертає через `Cookie`
- **HttpOnly** — JS не читає cookie (захист від XSS)
- **Secure** — cookie тільки через HTTPS
- **SameSite=Lax** — захист від CSRF для більшості сценаріїв
- **PHP**: `setcookie()` для запису, `$_COOKIE` для читання, `header()` для response headers
- **Symfony**: `$request->headers->get()`, `$response->headers->set()`, `Cookie::create()`
