### 1. Життєвий цикл HTTP-запиту, DNS

<details>
<summary>Розкрити:</summary>

На співбесіді можна відповідати так:

"Коли користувач вводить URL у браузері, спочатку браузер визначає, куди саме треба підключитися. Для цього він виконує DNS lookup і отримує IP-адресу домену. Далі браузер встановлює TCP-з'єднання з сервером, а якщо це HTTPS — ще й TLS handshake. Потім відправляє HTTP-запит: метод, headers, cookies, body.

Запит спочатку потрапляє на веб-сервер або reverse proxy, наприклад Nginx або Apache. Якщо це PHP-додаток, веб-сервер передає запит у PHP-FPM. Далі запускається application bootstrap: підключається конфіг, DI container, middleware, router. Роутер визначає, який controller/action або handler має обробити запит.

Потім виконується бізнес-логіка: валідація, авторизація, звернення до бази, кешу, черг, зовнішніх API. Після цього формується response: status code, headers, body. Веб-сервер повертає відповідь клієнту, а браузер її обробляє. Якщо це HTML — рендерить сторінку, якщо JSON — передає у frontend-код."

Якщо хочеш дуже коротко:
- DNS → знаходимо IP
- TCP/TLS → встановлюємо з'єднання
- HTTP request → відправляємо запит
- Nginx/Apache → PHP-FPM → app
- Router/controller/service/DB
- Response назад клієнту

---

#### Що таке DNS

"DNS — це система доменних імен. Вона перетворює зрозуміле людині ім'я, наприклад example.com, в IP-адресу сервера."

Простий приклад:
- ти відкриваєш google.com
- DNS каже: цей домен відповідає IP 142.x.x.x
- далі браузер йде вже по IP

---

#### Що таке DNS записи: A, MX, TXT

**A record** — пов'язує домен з IPv4-адресою.
```
example.com -> 192.168.1.10
```

**AAAA record** — те саме, але для IPv6.

**CNAME** — один домен вказує на інший домен.
```
www.example.com -> example.com
```

**MX** — показує, який поштовий сервер приймає пошту для домену.
```
example.com -> mail.example.com
```

**TXT** — текстовий запис. Часто використовується для SPF, DKIM, верифікації домену, різних технічних налаштувань.

"A record потрібен, щоб знайти IP сервера. MX — для доставки пошти. TXT — для службової інформації, наприклад SPF, DKIM або верифікації домену."

---

#### Як DNS кешується

"DNS кешується на кількох рівнях:
- у браузері
- в операційній системі
- у локального DNS resolver
- у провайдера або публічного DNS-сервера

Час життя кешу задається через TTL — Time To Live. Поки TTL не закінчився, стара відповідь може використовуватись із кешу без нового DNS-запиту."

Якщо для запису TTL = 300 секунд, то протягом 5 хвилин клієнт або resolver може використовувати кешований IP.

Якщо ти змінив IP домену, частина клієнтів ще якийсь час може ходити на старий IP, поки не закінчиться TTL.

---

#### Що буде, якщо впаде DNS

"Якщо DNS недоступний і запису немає в кеші, клієнт не зможе визначити IP адрес сервера, а значить — не зможе підключитися до сайту. Тобто сам application може бути живим, але користувачі до нього не дійдуть по доменному імені.

Якщо DNS уже був закешований, то якийсь час система може продовжити працювати, поки кеш не протухне."

Що саме ламається:
- сайт може "не відкриватися"
- API по домену стане недоступне
- зовнішні інтеграції не зможуть достукатись
- може перестати ходити пошта, якщо проблеми з MX
- сервіси можуть не знайти один одного по імені

Важлива думка для senior-співбесіди:

"DNS — це критична частина інфраструктури. Тому використовують redundancy, кілька NS, моніторинг, health checks, адекватний TTL і failover."

---

#### Що таке hosts

"Файл hosts — це локальна таблиця відповідності домену та IP на машині. Він має пріоритет над DNS. Якщо в hosts прописати домен вручну, система не буде питати DNS для цього домену."

Приклад:
```
127.0.0.1 my-project.local
```

Для чого використовується:
- локальна розробка
- тестування
- тимчасовий обхід DNS
- блокування або підміна адрес локально

"hosts працює тільки на конкретній машині. Це не глобальна зміна."

---

#### Як це все зв'язати в одну сильну відповідь

"Коли користувач відкриває сайт, спочатку система через DNS перетворює доменне ім'я в IP адресу. Якщо запис уже є в кеші браузера, ОС або DNS resolver, то використовується кешована відповідь згідно TTL. Якщо ні — іде запит до DNS. Після отримання IP встановлюється TCP-з'єднання, а для HTTPS ще виконується TLS handshake. Потім браузер відправляє HTTP-запит на сервер.

Запит потрапляє на Nginx або Apache, далі в PHP-FPM, після чого додаток проходить bootstrap, routing, middleware, controller і бізнес-логіку. У процесі можуть бути звернення до бази, Redis, зовнішніх сервісів. Після цього формується HTTP-відповідь і повертається клієнту.

DNS-записи бувають різні: A — для IP, MX — для пошти, TXT — для службової інформації. Якщо DNS впаде і запис не закешований, користувач не зможе знайти IP сервера і сайт не відкриється, навіть якщо сам сервер працює. Також локально DNS можна обійти через файл hosts, який має вищий пріоритет на конкретній машині."

---

#### Що можуть ще запитати поруч

**Чим DNS відрізняється від hosts?**
- DNS — глобальна система
- hosts — локальна ручна підміна

**Що таке TTL?**
- час, скільки DNS-відповідь живе в кеші

**Чому після зміни IP сайт у когось працює, а у когось ні?**
- через DNS кеш і TTL

**Якщо DNS упав, чи можна відкрити сайт по IP?**
- так, іноді можна, але не завжди
- можуть бути проблеми з HTTPS, virtual host, routing, Host header

**На якому етапі працює PHP?**
- після веб-сервера, коли запит передається в PHP-FPM

---

#### Коротка шпаргалка

**HTTP lifecycle**
```
DNS → TCP/TLS → HTTP request → web server → PHP-FPM → app → DB/cache/API → response
```

**DNS records**
- A = IPv4
- AAAA = IPv6
- CNAME = alias
- MX = mail
- TXT = text/service info

**Cache**
- browser → OS → resolver → provider DNS
- TTL визначає час життя

**If DNS fails**
- без кешу домен не резолвиться
- сайт/АПІ недоступні по імені
- по IP іноді можна, але не завжди

**hosts**
- локальна підміна домену на IP
- має пріоритет над DNS
- працює тільки на цій машині

</details>

### 2. Nginx vs Apache, Headers

<details>
<summary>Розкрити:</summary>

#### Nginx vs Apache

На співбесіді можна сказати так:

"Apache і Nginx — це веб-сервери, але вони по-різному обробляють запити.

Apache історично працює через process-based або thread-based модель: на запити виділяються окремі процеси або потоки. Він дуже гнучкий, добре підтримує .htaccess, але під великим навантаженням може споживати більше ресурсів.

“.htaccess — це файл, який дозволяє задавати правила для папки без зміни основного конфіга Apache. Через нього часто налаштовують rewrite rules, redirects, доступ, caching, headers.”

Nginx побудований на event-driven, asynchronous architecture. Він краще працює з великою кількістю одночасних з'єднань, споживає менше пам'яті, часто використовується як reverse proxy, load balancer і для віддачі статики.

У PHP-проєктах Nginx часто працює разом із PHP-FPM, а Apache може або також працювати з PHP-FPM, або через mod_php, хоча зараз частіше теж через PHP-FPM."

Дуже коротка різниця:

**Apache**
- гнучкий
- є .htaccess
- простіше для старих проєктів
- може бути важчим під high load

**Nginx**
- швидкий на статиці
- добре тримає багато конекшенів
- часто використовується як reverse proxy
- не читає .htaccess

Коли що краще:

"Якщо говорити про modern production setup, то найчастіше я очікую Nginx + PHP-FPM. Особливо якщо є high load, reverse proxy, caching, SSL termination, балансування.

Apache я частіше бачу в legacy-проєктах або там, де важлива гнучка per-directory конфігурація через .htaccess."

Сильна відповідь для senior:

"Головна різниця не тільки в тому, що один швидший, а інший повільніший. Важливіша різниця — в архітектурі обробки запитів. Nginx краще масштабується на велику кількість одночасних підключень і часто стоїть на фронті як reverse proxy. Apache більш гнучкий на рівні конфігурації директорій і історично був дуже популярний в PHP-екосистемі."

---

#### Що таке headers

"HTTP headers — це службова інформація, яка передається разом із HTTP-запитом або HTTP-відповіддю. Вони містять метадані: тип контенту, авторизацію, cookies, cache rules, user-agent, host та інше."

Приклади request headers:
- `Host`
- `Authorization`
- `Content-Type`
- `Accept`
- `User-Agent`
- `Cookie`
- `X-Request-Id`
- `X-Forwarded-For`

Приклади response headers:
- `Content-Type`
- `Cache-Control`
- `Set-Cookie`
- `Location`
- `X-Frame-Options`
- `Strict-Transport-Security`

---

#### Як витягнути headers у PHP

**Варіант 1. Через `$_SERVER`**

```php
$host = $_SERVER['HTTP_HOST'] ?? null;
$userAgent = $_SERVER['HTTP_USER_AGENT'] ?? null;
$authorization = $_SERVER['HTTP_AUTHORIZATION'] ?? null;
$contentType = $_SERVER['CONTENT_TYPE'] ?? null;
```

Більшість request headers у `$_SERVER` приходять у вигляді:
- з префіксом `HTTP_`
- у верхньому регістрі
- дефіси замінені на `_`

Наприклад:
```
X-Request-Id   → HTTP_X_REQUEST_ID
User-Agent     → HTTP_USER_AGENT
Content-Type   → CONTENT_TYPE  (без HTTP_)
```

**Варіант 2. Через `getallheaders()`**

```php
$headers = getallheaders();
$auth = $headers['Authorization'] ?? null;
```

"getallheaders() зручна, але я б не покладався тільки на неї у portable-рішенні, бо в різних оточеннях її поведінка може відрізнятись. Найнадійніше — або framework request object, або нормалізація через $_SERVER."

**Варіант 3. Через framework**

Symfony:
```php
$request->headers->get('Authorization');
$request->headers->get('X-Request-Id');
```

Yii2:
```php
$headers = Yii::$app->request->headers;
$auth = $headers->get('Authorization');
$requestId = $headers->get('X-Request-Id');
```

"У чистому PHP можна брати із `$_SERVER` або `getallheaders()`, але в реальному проєкті я зазвичай використовую request abstraction фреймворка, бо це читабельніше і менше шансів помилитися."

---

#### Як віддати response headers у PHP

```php
header('Content-Type: application/json');
header('X-Request-Id: 123');
http_response_code(200);

echo json_encode(['ok' => true]);
```

У framework це теж зазвичай робиться через response object.

---

#### Які headers часто питають на співбесіді

**Authorization** — для токенів:
```
Authorization: Bearer <token>
```

**Content-Type** — формат body:
```
application/json
application/x-www-form-urlencoded
multipart/form-data
```

**Accept** — що клієнт хоче отримати у відповіді.

**Host** — який домен запитували.

**X-Forwarded-For** — оригінальний IP клієнта, якщо запит іде через proxy або load balancer.

**X-Forwarded-Proto** — показує, чи був оригінальний запит `http` або `https`.

---

#### Важливий senior-момент про proxy

"У продакшені треба пам'ятати, що додаток часто стоїть за Nginx, load balancer або Cloudflare, тому клієнтський IP не завжди буде в `REMOTE_ADDR`. Часто треба дивитися `X-Forwarded-For`, але тільки якщо ми довіряємо proxy. Інакше це можна підробити."

---

#### Готова відповідь одним шматком

"Apache і Nginx — це веб-сервери, але вони відрізняються архітектурою. Apache історично використовує process/thread-based підхід і підтримує .htaccess, що зручно для legacy або гнучкої конфігурації. Nginx побудований на event-driven моделі, тому краще працює з великою кількістю одночасних з'єднань, добре віддає статику і часто використовується як reverse proxy перед PHP-FPM. У сучасних PHP-проєктах частіше використовується Nginx + PHP-FPM.

HTTP headers — це метадані запиту або відповіді. Наприклад, Authorization, Content-Type, Accept, Host, Cookie. У PHP їх можна витягувати через `$_SERVER`, наприклад `HTTP_AUTHORIZATION`, або через `getallheaders()`. У фреймворках краще використовувати request object, наприклад `$request->headers->get('Authorization')`. Для response headers можна використовувати `header()` або response object фреймворка."

---

#### Коротка шпаргалка

**Nginx vs Apache**
- Apache = process/thread based, .htaccess, legacy-friendly
- Nginx = event-driven, high concurrency, reverse proxy, static files

**Headers**
- це службові метадані HTTP
- бувають request і response headers

**Як читати в PHP**
- `$_SERVER['HTTP_AUTHORIZATION']`
- `getallheaders()`
- framework request object

**Важливо**
- за proxy справжній IP часто не в `REMOTE_ADDR`
- треба дивитися `X-Forwarded-For` обережно

</details>

### 3. Протоколи передачі даних: UDP, TCP, HTTP, HTTPS

<details>
<summary>Розкрити:</summary>

#### Що таке протоколи передачі даних

"Протокол передачі даних — це набір правил, за якими системи обмінюються інформацією по мережі. Різні протоколи вирішують різні задачі. Наприклад, TCP і UDP працюють на транспортному рівні, а HTTP і HTTPS — уже на рівні прикладного протоколу."

---

#### TCP

"TCP — це connection-oriented протокол. Перед передачею даних він встановлює з'єднання між клієнтом і сервером. Його головна перевага — надійність: він гарантує порядок пакетів, контроль доставки, повторну відправку втрачених пакетів."

- надійний
- перевіряє доставку
- зберігає порядок пакетів
- повільніший за UDP через overhead

Де використовується: HTTP/HTTPS, SMTP, FTP, бази даних, більшість веб-застосунків.

---

#### UDP

"UDP — це connectionless протокол. Він не встановлює повноцінне з'єднання перед передачею даних і не гарантує доставку, порядок або повторну відправку пакетів. Зате він швидший і має менший overhead."

- швидший
- простіший
- не гарантує доставку і порядок
- немає підтвердження отримання

Де використовується: стрімінг, онлайн-ігри, VoIP, DNS, сервіси де важливіша швидкість ніж ідеальна надійність.

---

#### Різниця TCP і UDP

"TCP — це про надійність, UDP — це про швидкість."

| | TCP | UDP |
|---|---|---|
| З'єднання | connection-oriented | connectionless |
| Доставка | гарантована | не гарантована |
| Порядок | збережений | не гарантований |
| Швидкість | повільніший | швидший |

---

#### HTTP

"HTTP — це прикладний протокол, який використовується для обміну даними між клієнтом і сервером у вебі. Наприклад, браузер відправляє HTTP request, а сервер повертає HTTP response.

HTTP сам по собі не займається доставкою пакетів — для цього він зазвичай використовує TCP як транспорт."

Що є в HTTP: method (GET, POST, PUT, DELETE), headers, body, status codes.

---

#### HTTPS

"HTTPS — це HTTP поверх TLS/SSL. Тобто це той самий HTTP, але з шифруванням. HTTPS забезпечує конфіденційність, цілісність даних і підтвердження автентичності сервера через сертифікат."

HTTPS дає:
- шифрування
- захист від підміни
- захист від перехоплення
- перевірку сертифіката сервера

"HTTP передає дані у відкритому вигляді, а HTTPS — у зашифрованому. Тому логіни, паролі, токени, cookies та інші чутливі дані повинні передаватися через HTTPS."

---

#### Важливий moment для senior-рівня

"Треба розуміти, що TCP/UDP і HTTP/HTTPS — це не прямі конкуренти. TCP і UDP — це транспортні протоколи, а HTTP і HTTPS — прикладні. HTTP зазвичай працює поверх TCP. HTTPS — це HTTP поверх TLS, а TLS теж зазвичай іде поверх TCP."

При HTTPS перед HTTP-запитом ще відбувається TLS handshake, у межах якого сторони домовляються про шифрування і перевіряється сертифікат сервера.

---

#### Готова відповідь одним шматком

"TCP і UDP — це транспортні протоколи. TCP встановлює з'єднання і гарантує доставку даних у правильному порядку, тому він надійний, але має більший overhead. UDP не встановлює повноцінне з'єднання і не гарантує доставку чи порядок пакетів, зате працює швидше і використовується там, де важлива мінімальна затримка.

HTTP — це прикладний протокол для обміну даними між клієнтом і сервером у вебі. Він зазвичай працює поверх TCP. HTTPS — це HTTP поверх TLS, тобто той самий HTTP, але із шифруванням. Основна різниця між HTTP і HTTPS у тому, що HTTPS захищає дані від перехоплення і підміни, а HTTP передає їх без шифрування."

#### Коротка шпаргалка

**TCP** — надійний, порядок пакетів, контроль доставки, повільніший

**UDP** — швидший, без гарантії доставки, без гарантії порядку

**HTTP** — протокол веб-запитів, request/response, зазвичай поверх TCP

**HTTPS** — HTTP + TLS, шифрування, безпечна передача даних

Де який використовують:
- TCP: веб, API, бази даних, пошта
- UDP: DNS, ігри, стрімінг, голосовий зв'язок
- HTTP: звичайний веб-протокол
- HTTPS: захищений веб-протокол, стандарт для продакшену
