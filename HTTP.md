### 1. Життєвий цикл HTTP-запиту

<details>
<summary>Розкрити:</summary>

На співбесіді можна відповідати так:

"Коли користувач вводить URL у браузері, спочатку браузер визначає, куди саме треба підключитися. Для цього він виконує DNS lookup і отримує IP-адресу домену. Далі браузер встановлює TCP-з'єднання з сервером, а якщо це HTTPS — ще й TLS handshake. Потім відправляє HTTP-запит: метод, headers, cookies, body.

Запит спочатку потрапляє на веб-сервер або reverse proxy, наприклад Nginx або Apache. Якщо це PHP-додаток, веб-сервер передає запит у PHP-FPM. Далі запускається application bootstrap: підключається конфіг, DI container, middleware, router. Роутер визначає, який controller/action або handler має обробити запит.

Потім виконується бізнес-логіка: валідація, авторизація, звернення до бази, кешу, черг, зовнішніх API. Після цього формується response: status code, headers, body. Веб-сервер повертає відповідь клієнту, а браузер її обробляє. Якщо це HTML — рендерить сторінку, якщо JSON — передає у frontend-код."

Якщо хочеш дуже коротко:
- DNS → знаходимо IP
- TCP/TLS → встановлюємо з'єднання
- HTTP request → відправляємо запит
- Nginx/Apache → PHP-FPM → app
- Router/controller/service/DB
- Response назад клієнту

#### Що таке DNS

"DNS — це система доменних імен. Вона перетворює зрозуміле людині ім'я, наприклад example.com, в IP-адресу сервера."

Простий приклад:
- ти відкриваєш google.com
- DNS каже: цей домен відповідає IP 142.x.x.x
- далі браузер йде вже по IP

---

#### Що таке DNS записи: A, MX, TXT

**A record** — пов'язує домен з IPv4-адресою.
```
example.com -> 192.168.1.10
```

**AAAA record** — те саме, але для IPv6.

**CNAME** — один домен вказує на інший домен.
```
www.example.com -> example.com
```

**MX** — показує, який поштовий сервер приймає пошту для домену.
```
example.com -> mail.example.com
```

**TXT** — текстовий запис. Часто використовується для SPF, DKIM, верифікації домену, різних технічних налаштувань.

"A record потрібен, щоб знайти IP сервера. MX — для доставки пошти. TXT — для службової інформації, наприклад SPF, DKIM або верифікації домену."

---

#### Як DNS кешується

"DNS кешується на кількох рівнях:
- у браузері
- в операційній системі
- у локального DNS resolver
- у провайдера або публічного DNS-сервера

Час життя кешу задається через TTL — Time To Live. Поки TTL не закінчився, стара відповідь може використовуватись із кешу без нового DNS-запиту."

Якщо для запису TTL = 300 секунд, то протягом 5 хвилин клієнт або resolver може використовувати кешований IP.

Якщо ти змінив IP домену, частина клієнтів ще якийсь час може ходити на старий IP, поки не закінчиться TTL.

---

#### Що буде, якщо впаде DNS

"Якщо DNS недоступний і запису немає в кеші, клієнт не зможе визначити IP адрес сервера, а значить — не зможе підключитися до сайту. Тобто сам application може бути живим, але користувачі до нього не дійдуть по доменному імені.

Якщо DNS уже був закешований, то якийсь час система може продовжити працювати, поки кеш не протухне."

Що саме ламається:
- сайт може "не відкриватися"
- API по домену стане недоступне
- зовнішні інтеграції не зможуть достукатись
- може перестати ходити пошта, якщо проблеми з MX
- сервіси можуть не знайти один одного по імені

Важлива думка для senior-співбесіди:

"DNS — це критична частина інфраструктури. Тому використовують redundancy, кілька NS, моніторинг, health checks, адекватний TTL і failover."

---

#### Що таке hosts

"Файл hosts — це локальна таблиця відповідності домену та IP на машині. Він має пріоритет над DNS. Якщо в hosts прописати домен вручну, система не буде питати DNS для цього домену."

Приклад:
```
127.0.0.1 my-project.local
```

Для чого використовується:
- локальна розробка
- тестування
- тимчасовий обхід DNS
- блокування або підміна адрес локально

"hosts працює тільки на конкретній машині. Це не глобальна зміна."

---

#### Як це все зв'язати в одну сильну відповідь

"Коли користувач відкриває сайт, спочатку система через DNS перетворює доменне ім'я в IP адресу. Якщо запис уже є в кеші браузера, ОС або DNS resolver, то використовується кешована відповідь згідно TTL. Якщо ні — іде запит до DNS. Після отримання IP встановлюється TCP-з'єднання, а для HTTPS ще виконується TLS handshake. Потім браузер відправляє HTTP-запит на сервер.

Запит потрапляє на Nginx або Apache, далі в PHP-FPM, після чого додаток проходить bootstrap, routing, middleware, controller і бізнес-логіку. У процесі можуть бути звернення до бази, Redis, зовнішніх сервісів. Після цього формується HTTP-відповідь і повертається клієнту.

DNS-записи бувають різні: A — для IP, MX — для пошти, TXT — для службової інформації. Якщо DNS впаде і запис не закешований, користувач не зможе знайти IP сервера і сайт не відкриється, навіть якщо сам сервер працює. Також локально DNS можна обійти через файл hosts, який має вищий пріоритет на конкретній машині."

---

#### Що можуть ще запитати поруч

**Чим DNS відрізняється від hosts?**
- DNS — глобальна система
- hosts — локальна ручна підміна

**Що таке TTL?**
- час, скільки DNS-відповідь живе в кеші

**Чому після зміни IP сайт у когось працює, а у когось ні?**
- через DNS кеш і TTL

**Якщо DNS упав, чи можна відкрити сайт по IP?**
- так, іноді можна, але не завжди
- можуть бути проблеми з HTTPS, virtual host, routing, Host header

**На якому етапі працює PHP?**
- після веб-сервера, коли запит передається в PHP-FPM

#### Коротка шпаргалка

**HTTP lifecycle**
```
DNS → TCP/TLS → HTTP request → web server → PHP-FPM → app → DB/cache/API → response
```

**DNS records**
- A = IPv4
- AAAA = IPv6
- CNAME = alias
- MX = mail
- TXT = text/service info

**Cache**
- browser → OS → resolver → provider DNS
- TTL визначає час життя

**If DNS fails**
- без кешу домен не резолвиться
- сайт/АПІ недоступні по імені
- по IP іноді можна, але не завжди

**hosts**
- локальна підміна домену на IP
- має пріоритет над DNS
- працює тільки на цій машині
